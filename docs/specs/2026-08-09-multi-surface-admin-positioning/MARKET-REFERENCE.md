# 公开多端产品形态参考：从“多端功能堆叠”到“角色化工作表面”

> 调研日期：2026-08-09 · 证据范围：产品方官方公开页面/规则/开发文档
>
> 本文用于产品定位，不用于反推淘宝、美团、携程或飞猪的内部技术架构，也不构成这些产品的功能复刻清单。

## 研究问题

1. 为什么一个平台会同时存在消费者端、商家/管理端、移动执行端和专项伙伴工具？
2. 当 Web 与 Mobile 面向同一角色时，哪些能力应该共享事实但不共享界面？
3. 如何避免把“手机不能做复杂操作”误写成单一安全规则？

## 对 Workbench 的架构结论

### 1. 按角色建立表面，而不是按设备复制页面

Workbench 只拥有三类可见工作表面：Web 管理控制中心、Mobile 角色执行端和专业工具。消费者/IM 前台虽可通过标准协议触达底座，但不进入 Workbench 的后台导航。

### 2. 同一领域事实，多个任务视图

同一个项目、工作项或审批对象可以在 Web 和 Mobile 出现，但必须共享对象标识、状态、权限结果与审计事实；两端分别提供适合该角色/时机的动作，不共享页面、路由或布局。

### 3. 用动作政策取代“重要操作只能 Web”的简单规则

- A：观察/提醒可按责任范围出现在多端。
- B：受控单对象执行可在 Mobile 闭环，前提是服务端重验、明确影响、确认、幂等与审计都可达成。
- C：批量、组织级、跨对象治理固定在 Web。
- D：机器、设备、进程、端口、编码等专业/物理动作固定在专业工具。

### 4. 专业工具是独立工作上下文，不是后台菜单的垃圾桶

DevSvc Host、Fleet、Coder 等应通过受控入口、授权和审计与控制中心关联；不把它们的完整页面复制进 Web 或 Mobile。

## 应用时的防误用清单

- 不把外部产品的 UI 视觉、菜单名称或业务领域当成 Axi Workbench 需求。
- 不因外部产品在手机端处理某个重要流程，就取消 Workbench 的 C/D 级边界。
- 不将 Web/Mobile 的共同登录、对象和通知，误实现为共同路由树或视口分支。
- 不将公开产品文案视为内部架构、技术栈、数据规模或安全实现的证据。
- 每项实施功能仍须通过 `CAPABILITY-OWNERSHIP.md` 完成 Workbench 自身的角色、动作、授权、审计与验收判断。
