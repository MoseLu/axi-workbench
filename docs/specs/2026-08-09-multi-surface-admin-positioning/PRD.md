# 多端后台产品架构定位 — 变更 PRD

## 背景

`Axi Workbench` 已有独立的 Web 与 Mobile 用户应用，但仅有工程隔离不足以解决产品混杂：若按屏幕尺寸切分，Web 会被设计成放大的移动端，Mobile 会逐步承担完整后台，Host 与专项工具也会被误放进用户导航。

本变更以淘宝/千牛、美团、携程 eBooking、飞猪商家中心的**官方公开多端产品形态**为参照。研究结论不是复制竞品能力，而是将 Workbench 定位为按角色和动作等级组织的“控制—执行—专业工具”系统。来源、推导和排除项见 [`MARKET-REFERENCE.md`](./MARKET-REFERENCE.md)。

## 目标

把项目级产品定位固化为：

1. **Web 控制中心**：完整后台管理的主端；负责 C 级管理与治理动作。
2. **Mobile 角色执行端**：整体管理中的辅助端，但可作为值班/现场角色的首选端；只闭环满足政策的 A/B 级任务。
3. **专业工具**：Host、Fleet、Axi Coder 等保留 D 级专业/物理操作，不能演变成第三个通用门户。
4. **共享底座**：以领域 API、动作政策、身份、审计和交接合同保持事实一致，绝不共享页面或布局。

## 成功标准

- `docs/state/PRD.md` 明确三类可见表面、共享底座、用户场景、动作等级、能力归属、交接与路线图。
- 每个新能力在开发前都有角色、A/B/C/D 动作等级、允许表面、服务端授权/重验、审计和交接记录。
- Mobile 的现有事实仍是“4 个常驻页 + 顶部 Scan 动作”；Mobile 可做受控单对象执行，但不吞入组织/批量治理。
- 同名但语义不同的扫码仍拆为 Web 通用识别与 Mobile 审批确认。
- TDD、TODO、Milestone、manifest、Handoff 和 Changelog 可追溯该架构决策。

## 不做什么

- 不移动源码、不合并两套 React 路由树、不移除 `@epap/*` / legacy UI 兼容层。
- 不建设消费者端、插件市场或第三方应用分发；这次研究不构成竞品功能路线图。
- 不把当前文档草案误报为已完成功能实现、用户研究或外部产品内部架构研究。
