## 1. 为什么需要这套体系（要解决的真实问题）

工作区已经推进到 30+ 个项目、6 个 Personal OS 能力模块，但存在一个反复出现的问题：

> **多轮迭代之后，会忘记自己当初为什么这样设计、边界划在哪里、哪个项目拥有哪块能力。**

根因不是"文档不够多"，而是：

1. 母 PRD 放在工作区外（桌面 `AXI-Personal-OS-PRD.md`），不在日常视野里，也不随实现更新。
2. 6 个核心能力模块（Kernel / Workbench CLI / Inbox / Sync / Runtime / Apps）没有自己的 PRD，设计只活在代码注释和零散 README 里。
3. 已有 PRD 风格、编号、颗粒度不统一，无法横向对照。
4. 缺少"决策记录"——只留下了"做成了什么"，没留下"为什么不那样做"。
5. PRD 与 AGENTS / HANDOFF / CHANGELOG / ADR / TODO 职责重叠，不知道该更新哪个，于是都不更新。

本宪章的目标是建立一套**低维护成本、单一入口、随迭代自然演进**的 PRD 体系，让任何一次"接手"（无论是几周后的自己，还是一个全新的 AI agent）都能在 10 分钟内重建设计上下文。

### 1.1 设计目标（这套体系必须做到）

- **单一入口**：从 `docs/prd/README.md` 能找到任何一份 PRD 与关键决策。
- **分层不重复**：愿景、产品线、项目、迭代各写一层，同一件事只在一个地方维护。
- **决策可追溯**：每个重要取舍都有一条"决策记录"，回答"为什么"。
- **状态可见**：每份 PRD 标明生命周期状态，过期文档主动标 Stale，而不是默默误导。
- **写得动、养得起**：模板足够具体（填空即可），维护节奏嵌入现有工作流，不依赖"有空再补文档"。

## 2. 四层 PRD 模型

文档按"抽象层级"分为四层。**上层规定方向与边界，下层承接实现；下层不得与上层冲突，冲突时以上层为准并发起上层修订。**

```text
L0  愿景总纲（Vision / Platform PRD）
    │   回答：我们在造什么、为谁、为什么、整体怎么分层、有哪些产品线
    │   数量：1 份（平台级）
    │
L1  产品线 PRD（Product Line PRD）
    │   回答：一条产品线（如 Personal OS 基础能力层 / 独立产品族）的目标、范围与路线图
    │   数量：少数几份，按产品线划分
    │
L2  项目 PRD（Project PRD）
    │   回答：一个仓库/项目的定位、职责边界、功能需求(FR)、契约、验收(AC)、架构
    │   数量：每个 canonical 项目 1 份，放在项目仓库内
    │
L3  迭代 PRD（Sprint / Feature PRD）
    │   回答：一次迭代或一个特性要解决的具体问题、范围、验收
    │   数量：按需创建，轻量，完成后归档
```

### 2.1 各层的存放位置

| 层级 | 存放位置 | 说明 |
|---|---|---|
| L0 | `docs/prd/01-AxiomaticWorld-Personal-OS-PRD.md` | 平台总纲，工作区唯一 |
| L1 | `docs/prd/` 下按产品线建档，或直接作为 L0 的章节 | 颗粒度不大时并入 L0，避免为分层而分层 |
| L2 | 各项目仓库内根目录 `PRD.md`（或 `docs/PRD.md`） | 项目自己拥有、自己提交 |
| L3 | 项目内 `docs/sprints/` 或孵化目录 | 临时文档，归档不删除 |
| 模板 | `docs/prd/templates/` | 项目级、迭代级两套 |

> **原则：能合并就不新增文件。** L1 只有在某条产品线复杂到 L0 装不下时才独立成文。当前阶段 Personal OS 六模块的"产品线视图"已浓缩在 L0 总纲的"子项目设计快照"章节。

### 2.2 模板继承（v1.1 起强制）

L2 项目 PRD **必须**继承 [`docs/prd/templates/PROJECT-PRD-TEMPLATE.md`](../docs/prd/templates/PROJECT-PRD-TEMPLATE.md)（当前版本 **v1.1**）。文首元信息块必须显式声明 `template_version` 与 `inherits` 两行字段，便于机器扫描与升版迁移。规则依据：`foundation/axi-rules/rules/prd-format/AGENTS.md`（AR-PRD-FORMAT-001 ~ 005）。补强点：

- §2 **分层理念 / 能力地图**必填（AR-PRD-FORMAT-002）
- §5 FR **必须**含数字阈值 / 结构计数 / 外部标准引用（AR-PRD-FORMAT-003）
- §5.1 多模块项目必须有"整合 X"收口 FR（AR-PRD-FORMAT-004）
- 模板升版触发 30 天迁移窗口（AR-PRD-FORMAT-005）

## 3. 编号规则

### 3.1 PRD 文档编号

- **平台总纲**：`PRD-00`（体系）与 `PRD-01`（平台总纲，沿用历史称呼）。
- **Personal OS 能力模块的历史编号沿用，不重新编号**（它们已在代码、测试、文档中被广泛引用）：

| 编号 | 模块 | 仓库 |
|---|---|---|
| PRD-01 | Kernel 内核 | `foundation/axi-kernel` |
| PRD-02 | Workbench CLI 工作台 CLI | `foundation/axi-workbench-cli` |
| PRD-03 | Inbox 资源收件箱 | `foundation/axi-inbox` |
| PRD-04 | Change Sync 变化同步 | `foundation/axi-sync` |
| PRD-05 | Governance Runtime 治理运行时 | `foundation/axi-runtime` |
| PRD-06 | Applications 应用层 | `foundation/axi-apps` |

- **新增项目 PRD**：编号格式 `PRD-<两位序号>`，序号在 `docs/prd/README.md` 索引中登记后生效，不复用已废弃编号。
- **L3 迭代 PRD**：格式 `<项目id>-SPRINT-<日期或序号>`，如 `axi-kernel-SPRINT-2026-09-repo-adapter`。

### 3.2 需求与验收编号（文档内部）

- 功能需求：`FR-<序号>`（Functional Requirement），如 `FR-3`。
- 验收标准：`AC-<序号>`（Acceptance Criterion），如 `AC-3`，尽量与 FR 对应。
- 目标：`G<序号>`（Goal）；非目标：`N<序号>`（Non-goal）。
- 跨文档引用需求时带项目前缀，如 `axi-kernel/FR-2`，避免编号撞车。
- 工作区级治理需求沿用历史 `REQ-*` 前缀（见 `docs/state/PRD.md`），不与 FR 混用。

## 4. 文档生命周期状态

每份 PRD 在文首元信息块中声明 `文档状态`，并在状态变化时更新：

| 状态 | 含义 | 进入条件 |
|---|---|---|
| **Draft** | 起草中，内容可能大幅变动 | 新建 |
| **Active** | 当前有效，指导实现与决策 | 评审通过、边界与验收明确 |
| **Stale** | 部分内容已落后于实现，需更新 | 审计发现文档与代码/注册表不一致 |
| **Deprecated** | 已被取代或项目已归档 | 有明确替代文档或项目进入 `archive/` |

### 4.1 状态纪律

- **不允许静默过期**：审计或迭代中发现 PRD 与现状不符，要么当场更新回 Active，要么先标 Stale 并在文首写明"哪里过期、以什么为准"。
- **Deprecated 必须指向替代物**：写明"被 XXX 取代"或"项目已归档至 XXX"，不留下断头文档。
- 状态变化本身是一次小提交，信息写进 `CHANGELOG.md`。

## 5. 维护节奏：什么时候必须动 PRD

把"更新 PRD"嵌入开发完成定义（Definition of Done），而不是事后补。**判断标准很简单：这次改动是否改变了"别人接手时需要知道的事实"。**

### 5.1 必须更新对应 PRD 的情形

- 新增 / 删除 / 调整一个对外能力或功能点（改 FR）。
- 修改项目职责边界、能力归属，或跨项目契约（改边界 + 契约，必要时发 ADR）。
- 修改核心对象模型 / Schema（L3 级变化，必须发 ADR）。
- 改变验收标准、验证命令、启动方式。
- 项目 promote（孵化→正式）、归档、合并、迁移路径。
- 做出一个"未来的自己很可能不理解"的取舍（加一条决策记录）。

### 5.2 不需要动 PRD 的情形

- 纯重构、改名内部变量、修 bug、调样式、补注释（这些进 `CHANGELOG.md` / 提交信息）。
- 临时调试、一次性脚本、实验性代码。

### 5.3 节奏建议（solo owner，轻量）

- **每次功能提交**：若触及 5.1，同提交或紧随其后更新 PRD，保持"代码与文档同批落地"。
- **每日 Reflection（已有）**：`axi-runtime` 的 Daily Reflection 产出当日变化，顺带提示"哪些 PRD 可能需要更新"。
- **每次接手 / 阶段收尾**：按 `AGENTS.md` 的 handoff 链跑一遍，并刷新 `docs/prd/README.md` 索引的"最后更新"。
- **窗口（季度）收尾**：集中清理 Stale 文档、更新 L0 的"当前实现状态"。

> 不设"文档冲刺日"。文档是工作的副产物，不是独立运动；模板和触发条件保证它在正常节奏里被顺手完成。

## 6. PRD 与其他文档的职责边界（避免重复维护）

工作区已有一套文档约定，PRD 必须与它们分工明确。**同一条信息只在一个权威文档里写，其他地方只引用、不复述。**

| 文档 | 回答的问题 | 拥有的内容 | 与 PRD 的关系 |
|---|---|---|---|
| **PRD（L0–L3）** | 造什么、为谁、为什么、边界、验收 | 目标、需求 FR、非目标、验收 AC、产品架构、决策摘要 | 产品事实的权威源 |
| **ADR** | 为什么做这个（架构/边界）决策 | 单个重要决策的背景、选项、结论、后果 | PRD 引用 ADR；ADR 承载决策细节 |
| **AGENTS.md** | agent / 协作者如何在本项目工作 | 读写范围、阅读顺序、验证命令、路由规则 | 引用 PRD 的边界，不重复需求 |
| **README.md** | 这是什么、怎么快速跑起来 | 一句话定位、快速开始、常用命令 | 是 PRD 的"门口告示"，指向 PRD |
| **docs/HANDOFF.md** | 现在做到哪、下一步是什么 | 当前工作、未决项、排障、契约指针 | 承接 PRD 的"当前进度切片"，变化最快 |
| **CHANGELOG.md / CHANGE.md** | 已经发生了什么 | 按版本/时间的变更记录 | PRD 描述"应然"，CHANGELOG 记录"实然" |
| **TODO.md / TASK.md** | 还要做什么 | 任务队列，绑定 FR/REQ ID | 任务来源于 PRD 的需求 |
| **MILESTONE.md** | 阶段性交付证据 | 里程碑与完成证据 | 对照 PRD 验收标准记录达成情况 |
| **TDD.md** | 怎么验证 | 测试设计、验证命令 | 支撑 PRD 验收标准的可执行化 |

### 6.1 一条信息该写在哪（速查）

- "这个项目是干什么的、有哪些功能" → **PRD**
- "为什么选 A 不选 B" → **ADR**（PRD 里只放一行摘要 + 链接）
- "现在卡在哪、下一步做啥" → **HANDOFF**
- "这次提交改了啥" → **CHANGELOG / 提交信息**
- "怎么跑测试" → **README / TDD / AGENTS**（PRD 引用，不复制命令清单）

## 7. 决策记录规范（ADR：捕捉"为什么这么设计"）

"遗忘设计"最致命的是遗忘**决策理由**。所有重要取舍必须沉淀为 ADR（Architecture / Decision Record）。

### 7.1 什么决策值得记

满足任一即记录：影响项目边界或对象模型；存在两个以上合理选项且未来可能反复；一旦遗忘会导致返工或错误回退；跨项目 / 跨团队契约。

不必记录：显而易见的实现选择、纯个人偏好且无后果、临时方案（临时方案写 HANDOFF）。

### 7.2 ADR 结构（一文件一决策）

1. **标题 + 状态**（Proposed / Accepted / Deprecated / Superseded by ADR-xxx）
2. **Context（背景）**：当时面对的问题与约束，尽量基于事实。
3. **Decision（决策）**：明确的结论。
4. **Alternatives Considered（考虑过的选项）**：至少列出被放弃的主要方案及原因。
5. **Consequences（后果）**：这个决策带来的正面影响、代价与后续约束。

### 7.3 ADR 存放与索引

- 工作区级 ADR：`foundation/workspace-governance/docs/adr/`（当前 ADR-001 ~ ADR-010）。
- 项目内部决策：项目内 `docs/adr/`。
- ADR **只追加、不改写历史结论**；决策被推翻时新增一条 ADR 并把旧条目标 Superseded，保留推理链。
- L0 总纲维护一份"关键 ADR 速览"，但细节以 ADR 原文为准。

### 7.4 现有 ADR 速览（截至 2026-09-25）

ADR-001 治理仓库作为索引平面；ADR-002 渐进式仓库命名；ADR-003 工作区根是非 Git 容器；ADR-004 apm-agent-context 包分层；ADR-005 agent-bff 归属；ADR-006 网关分类法；ADR-007 命名别名契约；ADR-008 Personal OS 仓库拓扑与边界冻结；ADR-009 工作流优先的有界 agent；ADR-010 可观测性治理。

## 8. 标准 PRD 应包含的章节

不同层级可裁剪，但一份**项目级 PRD（L2）**必须**结构化继承** [`PROJECT-PRD-TEMPLATE.md v1.1`](../docs/prd/templates/PROJECT-PRD-TEMPLATE.md)，至少覆盖以下要素（编号对齐模板）：

1. 文首元信息：编号、状态、**`template_version: v1.1`**、**`inherits`**、Owner、创建/更新时间、受众（AR-PRD-FORMAT-001）。
2. 一句话定位（§1）与边界（§1.1）。
3. **分层理念 / 能力地图**（§2）——核心能力分层表达，下层不成立上层必崩（AR-PRD-FORMAT-002）。
4. 背景与要解决的问题（§3）。
5. 用户与核心场景（§4）。
6. 目标与非目标（§5）。
7. 功能需求表（§6 FR-x，含优先级 P0/P1/P2）+ **每行 FR 必须含量化锚点**（AR-PRD-FORMAT-003）。
8. **多模块项目**必须有"整合 X"**模块收口 FR**（§6.1，AR-PRD-FORMAT-004）。
9. 架构与对象/数据模型（§7，必要时配图）。
10. 对外契约与依赖（§8 provides / consumes，链接到 `workspace.graph.json`）。
11. 关键决策摘要（§9，指向 ADR）。
12. 验收标准（§10 AC-x，可观察、可验证）。
13. 验证命令（§11，指向 README/TDD，不复制长清单）。
14. 未决问题（§12 Open Questions / Unknowns）。
15. 路线图与当前状态（§13，进度引用 HANDOFF / MILESTONE）。
16. 变更记录（§14）。

> L3 迭代 PRD 只保留：问题、范围（做/不做）、需求、验收、未决项——见迭代模板。

## 9. 写作风格要求

- **以用户价值和边界表述需求**，用主动语态、可验证的陈述句："系统应……（可观察证据）"，避免"支持/优化/可能"等无法验收的模糊词。
- **每个数字可追溯**：计数、比例、性能数字注明来源与口径；估算明确标注"估算"。
- **FR 行内必须含量化锚点**——数字阈值 / 结构计数 / 外部标准引用——作为强约束（AR-PRD-FORMAT-003）。
- **区分事实与推断**：声明关系（来自注册表）与推断关系（来自扫描）必须分开标注。
- **不写敏感信息**：凭据、密钥、令牌、个人隐私不入任何 PRD（见 `docs/governance/SECURITY.md`）。
- **中文为主体，术语保留英文**：品牌 `Axi` 不翻译；FR/AC/ADR 等 ID 一律英文。
- **短而密**：优先表格、清单、图；不复述代码，不贴大段源码。
- **继承而非复制**：L2 PRD 不应手抄模板正文，而是从模板复制再保留结构（见 §2.2 与 `foundation/axi-rules/rules/prd-format/AGENTS.md`）。
