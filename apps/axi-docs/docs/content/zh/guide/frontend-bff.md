## 摘要

BFF（Backend for Frontend）是为某一种前端体验专门设置的服务端适配层。它位于浏览器、移动端或桌面端与领域 API 之间，把前端的交互意图转换为后端调用，聚合多个数据源，并返回适合该前端直接消费的 DTO。

BFF 不是把业务逻辑搬到“前端项目”里，也不是一个换名字的 API Gateway。它的价值在于隔离前端体验与后端领域服务的差异，同时把认证边界、数据裁剪、错误语义和可观测性放在一个可治理的位置。

本页是后续引入的参考基线，不代表工作区当前已经统一采用 BFF。

## 典型形态

```text
浏览器 / 移动端 / 桌面端
          |
          v
  BFF-Web / BFF-Mobile / BFF-Admin
   - 会话与权限边界
   - 请求校验与协议转换
   - 聚合、裁剪和前端 DTO
   - 超时、缓存、错误与观测
          |
          v
  领域 API / 服务 / 工作区能力提供方
          |
          v
       领域数据源
```

一个前端体验可以有一个 BFF，也可以按边界拆成多个 BFF。关键是每个 BFF 都有明确的消费者、责任范围和服务级目标，而不是建立一个所有客户端共用的“万能聚合层”。

## BFF 与相邻模式的区别

| 模式 | 主要职责 | 是否面向单一前端体验 | 典型返回内容 |
| --- | --- | --- | --- |
| 前端直连领域 API | 直接消费后端资源 | 否 | 领域资源原形 |
| API Gateway | 路由、认证入口、限流、基础观测 | 否 | 通常透传或轻量转换 |
| BFF | 体验专属聚合、DTO、错误和交互语义 | 是 | 一个页面或流程需要的视图模型 |
| SSR / Server Components | 在服务端生成页面或组件 | 不一定 | HTML、组件数据或渲染结果 |

BFF 可以部署在 API Gateway 后面。Gateway 负责跨客户端的基础治理，BFF 负责某个前端体验的语义；两者不应把同一套职责重复实现。

## 什么时候值得引入

满足以下任一情况时，BFF 通常有明显收益：

- 一个页面或用户流程需要组合多个领域 API，且组合关系属于这个前端体验。
- 后端资源模型不适合前端直接使用，需要字段裁剪、命名转换、分页转换或状态归一化。
- Web、移动端、桌面端对认证方式、网络条件、负载形态或数据密度有不同要求。
- 前端需要稳定的体验契约，而领域服务仍在演进，不能让每次后端变更都扩散到客户端。
- 需要把上游凭证、内部地址或服务拓扑留在服务端。

以下情况不应为了“架构完整”而强行增加 BFF：

- 前端只调用一个稳定且已经面向客户端设计的 API，没有聚合或转换需求。
- BFF 只是把请求原样转发一遍，既没有体验边界，也没有治理价值。
- 需求本质是跨用户、跨系统的长事务、异步任务或数据同步，应由领域服务、工作流服务或事件系统负责。
- 团队没有明确的运行、告警和契约维护责任人。

## 边界：应该做什么，不应该做什么

### BFF 应该做

- 根据前端场景设计资源或动作接口，而不是暴露数据库表结构。
- 校验输入，解析会话，向下游传递最小必要的用户身份上下文。
- 并行调用独立下游，组合结果，并定义必需数据与可选数据的降级语义。
- 把领域响应映射为稳定、可裁剪、可版本化的前端 DTO。
- 统一前端可理解的错误码、请求 ID、分页和时间格式。
- 只对明确安全且幂等的读请求做短缓存或受控重试。
- 记录路由级日志、指标和 trace，能定位到具体下游依赖。

### BFF 不应该做

- 复制领域服务的核心不变量，或成为新的业务事实来源。
- 直接访问不属于它的数据库，绕过领域服务的权限和事务边界。
- 把所有客户端的差异塞进一个巨大条件分支，形成“万能 BFF”。
- 把长耗时业务流程、跨服务事务或定时任务偷偷放在同步请求里。
- 把上游错误、内部堆栈、访问令牌或服务地址原样返回给客户端。
- 用无界并发、无超时的 fan-out 把一次页面请求放大成下游雪崩。

## 接口设计基线

### 1. 以用户意图组织接口

优先使用前端场景能理解的接口，例如 `GET /api/web/v1/dashboard` 或 `POST /api/web/v1/orders/{id}/cancel`。不要把多个领域服务的 URL 拼接规则暴露给前端，也不要让前端决定聚合顺序。

### 2. DTO 是契约，不是领域对象转储

BFF 返回的字段应由页面或流程需要驱动。字段命名、可空性、枚举、时间格式、分页结构和排序语义都要明确。只新增向后兼容字段；删除或改变含义时使用版本或迁移窗口。

### 3. 明确必需与可选依赖

页面主数据失败时通常返回明确错误；推荐、统计、未读数等附属模块可以在契约允许时返回空值或 `degraded` 状态。不要让一个非关键下游的短暂故障把整个页面变成不可用，也不要静默吞掉关键数据失败。

### 4. 统一错误形态

建议至少包含：

```json
{
  "code": "PROFILE_UNAVAILABLE",
  "message": "暂时无法加载个人信息",
  "requestId": "req_...",
  "details": {}
}
```

`message` 面向用户或前端展示，`code` 面向程序分支，`requestId` 用于排障。上游 HTTP 状态、堆栈和内部服务名应留在服务端日志，不应直接透传。

### 5. 写操作必须考虑幂等性

创建、提交、支付、取消等操作应设计幂等键、重复提交行为和超时后的查询路径。BFF 可以转换协议，但不应伪造“已经成功”的业务结果。

## 可靠性与性能

每个下游调用都应有独立 deadline，同时设置整条 BFF 请求的总 deadline。推荐按下表处理：

| 能力 | 基线 | 注意事项 |
| --- | --- | --- |
| 超时 | 总超时小于前端可接受等待时间 | 下游 deadline 必须短于总 deadline |
| 重试 | 只对幂等、可判定为瞬时失败的请求重试 | 限次数、退避并加入抖动，禁止重试业务拒绝 |
| 并发 | 独立下游可以并行，但设置 fan-out 上限 | 避免一个请求无界创建任务 |
| 隔离 | 对慢依赖设置 bulkhead、连接池或并发上限 | 防止拖垮其他接口 |
| 缓存 | 只缓存可接受短暂陈旧的数据 | 明确 TTL、失效策略和用户隔离 |
| 降级 | 为非关键模块定义空态或 `degraded` | 降级必须可观测，不能静默丢数据 |

`Promise.all` 不是默认的可靠性策略。对有可选依赖的页面，应分别标记必需与可选结果，并为部分成功定义稳定 DTO。

## 安全边界

BFF 是浏览器与内部服务之间的信任边界，至少应落实：

- 浏览器只携带面向 BFF 的会话或短期凭证；上游服务令牌由服务端管理，禁止下发到浏览器。
- 校验来源、会话、租户和资源权限，不把客户端传来的用户 ID 当作可信身份。
- 使用 allowlist 限制可访问的下游主机或路径，避免把 BFF 变成 SSRF 代理。
- 对 Cookie 会话配置 CSRF 防护、SameSite、Secure、HttpOnly 和合理的过期策略。
- 对响应做字段白名单裁剪，尤其是内部 ID、权限信息、审计字段和凭证相关字段。
- 记录认证失败、权限拒绝、敏感写操作和异常下游调用，但日志不得包含令牌或完整隐私数据。

## 可观测性

按 BFF 路由建立最小指标集：请求量、成功率、4xx/5xx、p50/p95/p99 延迟、超时、降级次数、缓存命中率和下游错误分布。日志至少带 `requestId`、用户或租户的不可逆标识、路由、版本和下游依赖名；trace 应能把一次页面请求串到具体下游调用。

## 测试策略

- **DTO 与错误单元测试**：覆盖字段裁剪、枚举映射、分页、时间格式和上游错误映射。
- **下游契约测试**：验证 BFF 依赖的 provider 仍满足请求和响应契约，避免只靠 mock 掩盖漂移。
- **路由行为测试**：用真实 HTTP 入口验证认证、参数校验、必需/可选依赖和状态码。
- **集成测试**：用可控的下游替身验证并发、超时、重试、部分失败和幂等行为。
- **前端验收测试**：至少覆盖一个真实页面或流程，确认 DTO 变化反映为正确的加载、空态和错误态。
- **运行验证**：上线前确认健康检查、指标、日志和 trace 能在本地或测试环境中看到。

不要把“BFF 能返回 200”当作完成标准；真正要验证的是前端用户可见行为和异常路径。

## 渐进式引入路径

1. 选定一个前端体验和一个高收益场景，记录现有直连 API、权限和依赖。
2. 写出页面需要的 DTO、错误码、超时、降级和可观测性契约。
3. 实现最薄的一条 BFF 路由，先只迁移一个页面或流程。
4. 对下游调用加入 deadline、权限传递、日志和指标；为可选依赖补齐降级测试。
5. 在测试环境比较直连与 BFF 的成功率、延迟、错误和数据一致性。
6. 迁移一个切片后再扩展，删除旧的直连路径，避免两套契约长期并存。
7. 当 BFF 的边界稳定后，再决定是否拆分 Web、Mobile、Admin 等体验，或把共享能力下沉回领域服务。

## 工作区引入检查表

- [ ] 已写明 BFF 服务对应的前端体验和唯一主要消费者。
- [ ] 已列出它负责的页面/流程，以及明确不负责的领域规则。
- [ ] 每个下游依赖都有 owner、契约、超时和失败语义。
- [ ] DTO、错误码、权限传递、幂等和版本策略已经评审。
- [ ] 已定义路由级健康检查、指标、日志、trace 和告警入口。
- [ ] 已覆盖正常、空态、权限拒绝、超时、部分失败和重复提交。
- [ ] 已有渐进式迁移、回滚和旧直连路径下线条件。
- [ ] 如果跨工作区项目协作，已在对应项目文档或 workspace graph 中登记 provider/consumer 关系。

## 结论

BFF 的判断标准不是“多加一个后端服务”，而是是否为某个前端体验建立了清晰、稳定、可观测的服务端契约。优先从一个有真实聚合或安全边界问题的场景开始，保持 BFF 薄、领域能力归属清楚、异常语义显式，再根据运行证据决定是否扩大范围。
